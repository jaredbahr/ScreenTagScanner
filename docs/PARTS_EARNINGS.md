# Approved PK earnings, not retail prices or package counts

User confirmed PK means shop earnings at **2026-10-13 03:36 UTC**, with the current 2024 reference verified by the cloud worker. Spring pins SKU 580602 are **each**: 35 × $0.50 = **$17.50 total**. Pins are $2.00 each to the customer (Kirsten, 2026-10-22), so a pins line with no written quantity is counted from its dollar total ÷ $2.00 ("580602 $2.00" = 1 pin = $0.50); anything else stays manual. That whole-group amount is credited once, with a total/first-row reference on each sibling, never multiplied by a sequence such as 3 of 11. Since 0.13.31 one exception: $0.50 hardware (580602/580603/580604/580607) written once for a group is split evenly per frame when the count divides by N and the line is marked for the group, or unmarked at exactly 2 per frame with more than 4 in all (Kirsten, 2026-10-27). Each frame's share has its own receipt; a group paid whole before 0.13.31 is never split on top; a second pins line for the same group reuses its split; a frame whose phone (from the Scans log) differs is never paid; frames are only credited on the active month's tab, and the pins row's note lists the frames still to come.

`Parts.gs` encodes only approved earnings: spring pins/clips/plastic tabs/turn buttons $0.50 each; corners $2, latches $2.50, rollers $6, patio corners $5, Pella corners $2, Sears corners/latches $3, Anderson rollers $9, frame spreaders $2; new-screen corners $1.50 per SET OF FOUR; assembly $2.25 per SIDE/PIECE; pet-grille installation $8/job; wood-frame extra labor $11/job. Exact SKUs are in PART_EARNINGS. No glass-material retail prices are encoded or inferred.

The extractor supplies literal `parts` entries: exact SKU, explicit integer quantity (0 when uncertain), unit, whole-group flag and raw line. Known each-SKU quantities can use their confirmed each basis. Set/side quantities require compatible explicit units; a single known job can use its job basis. Unknown SKU, missing/unclear/duplicated quantity, unsupported units, >30 lines or >1000 quantity, and unclear group identity are held for manual review. No SKU is invented from generic "pins", no tag/frame counter becomes a parts quantity, and no fractional set-of-four inference is made.

The selected first eligible row carries a whole-group/tag/form total once; siblings and later frames show references without duplicate amount. Current group scope is store/ticket/tag-count (or a recognized multi-frame build form). Per-form quantities are not repeated across every build row. New-build assembly/corner lines that may already be covered by the existing $9 labor/$1.50 base stay manual instead of double-counting. Existing standard labor/material/zero-PK rows are excluded from extras. Uncertain spline reference/footnote codes do not override the existing spline formulas. Known extras earnings go into screen Earning or window Other Earn, except assembly (580625), which is added to screen LB Earn since 0.13.29 (receipt in the LB Earn note); standard window labor remains unchanged.

Receipts are reserved in the new earnings cell's note BEFORE the amount write and marked posted afterward. A receipt must contain a valid approved SKU/quantity/rate/amount and identity, and match its actual tab/block/row, customer, ticket and posted earning value. A group/ticket with a different customer identity is held for manual allocation, not silently treated as already paid. Malformed JSON or malformed receipt shape is a review case. Shared ScriptLock and scope/SKU receipt lookup prevent repeat credit. Interrupted pending receipts are held instead of charged again. Manual changes to existing earnings are not silently corrected. This is not a distributed spreadsheet transaction: uncertain receipts need owner reconciliation.

Scans Notes retain audit copies but are **never payment authority**. OCR text matching the reserved receipt marker is explicitly prefixed `Literal OCR:` in note fields so it cannot be parsed as a generated receipt. The earnings-cell receipt is written separately after that escaped human text. A forged OCR note claiming payment on an unrelated/nonexistent row cannot suppress a legitimate amount.

Literal extras without structured parts evidence, including `parts: []`, require earnings review. Every exact rescan with a newly unposted parts item requires manual earnings reconciliation, even if the first scan was clean. This includes a newly recognized pins line and a second SKU added after pins were already credited. Existing row values/notes are not automatically repaired or credited by a rescan. Ordinary rescans and rescans whose parts are fully credited remain clean. Contradictory per-tag/group evidence, explicit literal SKU/quantity disagreements and missing structured SKUs require review; ambiguous allocations are held. Explicit unrelated group SKUs may coexist with separately supported per-tag parts. Correctly identified group parts still earn once, with sibling references.

The raw provider schema uses supported structural types, enums and descriptions. The 30-line and 1–1000 quantity limits remain in the prompt and local calculation checks; unsupported `maxItems`, `minimum` and `maximum` are not sent. A regression captures the serialized UrlFetchApp request with an inert fake provider. See [Anthropic structured-output schema handling](https://platform.claude.com/docs/en/build-with-claude/structured-outputs#json-schema-limitations). No paid compatibility probe was made.

Scans structure, date rules, previous-month files, customer screening/glass prices and formula columns are preserved. All tests use synthetic data, no real images/API spending. OCR confidence and reference transcription still require ordinary review; these tests do not certify every photo. Build-base overlap, unclear units and unrecognized parts deliberately remain review cases.

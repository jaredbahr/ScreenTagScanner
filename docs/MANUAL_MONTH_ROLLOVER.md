# Manual month rollover in Settings

The normal scanner stays compact. **Settings → Review month → Start new month** shows the current workbook/month and asks for an explicit month/year (2000–2100). The SAME scanner password must be freshly entered in a separate masked field for every change. That field is never saved, logged, or placed in a URL and is cleared on submit, Back/cancel and page exit. Read-only Settings can load with existing scanner authentication; rollover never automatically uses the remembered scanner token. Server validation establishes possession of the shared password, not proof of physical typing or a separate admin identity.

Sync all candidate production files, including **MonthArchive**; preserve the existing manifest and deployed URL. Queue this deployment only after the current migration and temporary helpers are fully verified/removed. Keep the existing URL, private script and secrets unchanged. This feature does not start a month during deployment or install triggers.

## Safe behavior

- Both Settings RPCs validate the shared password. `startMonth` revalidates the supplied confirmation password, requires the reviewed current-workbook ID, checks migration gates, and holds the same ScriptLock used by scan writers/migration. Only `getMonthSettings`, `startMonth`, `scanTag` and the normal doGet/doPost endpoints are public; all helpers remain private.
- A copy is made from the distinct, migrated TEMPLATE only after blank-input/notes, complete headers/counters and formula checks. Allowed formula-only fields are existing screen spline formulas and the preserved Joliet Other formula. No current/previous month is cleared. Existing data and TEMPLATE remain untouched.
- A uniquely named staging copy is created in the configured monthly folder. Its access, copied layout/formulas and blank inputs are verified; it is then named with the full month and year, e.g. **October 2026**. Previous-month Totals must archive successfully as a single-page PDF in that folder before `SHEET_ID` switches. See [PDF archival behavior](MONTHLY_TOTALS_PDF.md).
- **Monthly folder (Jared, 2026-10-19):** set **`MONTH_FOLDER_ID`** to a Drive folder shared with Kirsten by name. New months are created inside it and inherit its people, so no per-month sharing is needed; the copy is accepted only if its access is the owner, the folder's people and `MONTH_EDITORS`. A folder shared by link is refused. Keep the TEMPLATE outside the folder (a stray edit in it blocks Start new month). Move existing files into the folder rather than copying them: the script finds files by ID, and a copy is a different file.
- **Sharing (Jared, 2026-10-14):** set the Script Property **`MONTH_EDITORS`** to up to 5 comma-separated email addresses (e.g. Kirsten's). Each new month is shared with exactly those people as **Editor**, after the copy is verified and **before** it becomes active, so scans never land in a file they can't open. Nobody else is added, and the old month and the template are never touched. If sharing fails, the new month is not activated; tapping Start again finishes it without a second copy. Unset = only the owner and inherited monthly-folder people have access. Settings shows the list masked (ki***@gmail.com). Google may send its usual "shared with you" email; that comes from Drive, not the scanner.
- Per-month completion receipts make same-month double clicks/retries return the already-active file without duplicates. A prior archived month is not silently reactivated. An unregistered monthly-folder file with the full target name or legacy `Screens YYYY-MM` name blocks creation for owner review.
- The default `MAX_MONTH_COPIES_PER_DAY` is **2**, configurable as a nonsecret integer **1–12**. Creation attempts, including failures, reserve that quota; recovering an existing operation does not consume another creation slot. The UI disables controls during a pending change and performs no automatic retries.
- Scans admitted before rollover retain their original workbook ID. Rollover waits for live admitted scans to finish, then snapshots Totals before switching. Expired orphan leases recover automatically; the write fence prevents expired requests writing afterward. New scans are blocked while an unresolved rollover journal exists.

## Recoverable state

`ROLLOVER_PENDING` is saved before a copy call with a unique operation/staging name and original active/template IDs. Copy ID, verification stage, active month and completion receipt are written in order. If creation returns an uncertain result, retry searches for the same staging file. It never blindly issues a second copy when an earlier copy cannot be found. Copy-verification errors retain the created file and do not activate it. Switching/bookkeeping failures recover the same file; already-activated manual data is preserved.

The UI says to reload Settings and review the **same** pending month after an interrupted response. A different target or unrelated active/template change is refused. No rollback deletes a file or clears a previous workbook. If a copy definitively never existed, the owner must inspect Drive/execution history, set nonsecret `ROLLOVER_NO_COPY_CONFIRMED` to the pending operation ID, then deliberately run private `abandonUncreatedRollover_`. It refuses any known/visible copy or active-ID drift; it removes only the uncreated-operation markers, never a Drive file. This attestation is a manual reconciliation step, not an automatic retry. Do not use it on an uncertain still-running operation.

Human Script Property/Sheet edits do not honor ScriptLock. Avoid manual configuration/template edits during rollover. An API copy and property writes are not a distributed transaction; the persistent gate/receipts make incomplete states fail closed and recoverable rather than pretending every failure leaves the old workbook active.

Do not expose or invoke the old private `startNewMonth_`/monthly trigger path for this UI. The manual workflow does not use it.

## Evidence

`tests/month-rollover.test.cjs` uses fake Drive/property/workbook services and synthetic data to cover tokens, malformed months, stale state, migration/concurrency, blank/template/layout checks, private copies, creation uncertainty, switch/cleanup failures, idempotence, prior-file preservation, copy limits and in-flight scan pinning. `tests/upload-ui.test.cjs` covers separate Settings, Back/cancel, explicit fresh confirmation, pending/double-click handling, no confirmation persistence and accessibility structure. No real Google file, API extraction, credential or rollover is created by these tests. Live phone layout, Drive ACL behavior and actual rollover require a separate authorized cloud/device verification.

## Store tab display names

The four numbered tabs may retain their historical names or use `Downers Grove`, `Lockport`, `Plainfield`, and `Joliet`. The scanner and template checker accept exactly one alias per store; duplicate old/city aliases fail closed. Store receipt and migration identities remain stable across a rename. Deploy compatible code before any title-only rename, drain scans, and verify Sheets updated direct Totals references with unchanged values/formula counts and sheet IDs. Do not rename while a rollover or sequence migration is pending. Tab colors are workbook formatting and remain unchanged by this code.
